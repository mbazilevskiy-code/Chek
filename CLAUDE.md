# Проект «Чек» (Chek) — контекст для Claude Code

Это файл-память проекта. Claude Code читает его при старте, чтобы сразу понимать, что мы
строим, как устроен код и как публиковать изменения. Держи его в актуальном состоянии.

## Что это

**«Чек»** — персональный AI-health-ассистент в Telegram. Пользователь присылает фото еды —
бот считает КБЖУ и оценивает питание по принципам Пола Чека (цельная еда). Плюс вода,
тренировки (турник/брусья), БАДы, самочувствие, анализы крови (по фото/PDF), кольцо Oura.

**Главный трек — white-label для тренеров («Чек Про»).** У каждого тренера свой бот под
его брендом; клиенты присылают боту данные, тренер видит их в веб-кабинете со «светофором»
и получает AI-брифы недели с готовым черновиком сообщения клиенту. Продаём тренерам, а не
конечным людям: их клиенты — уже платящая аудитория, а личность тренера — ядро доверия.

Философия рекомендаций: подход Пола Чека + доказательная нутрициология. Тон — тёплый,
по-русски, на «ты». **Медицинская граница:** продукт трекает и даёт lifestyle-советы, но
не ставит диагнозы и не назначает лечение; в разборах анализов и БАДов это проговаривается.

Полное видение и ТЗ — в артефакте (v0.4), у владельца есть ссылка и PDF.

## Стек

- Python 3.11+, **aiogram 3** (Telegram), **aiohttp** (веб-дашборд + кабинет + Oura OAuth),
  **anthropic** (Claude API), SQLite (одна база `food_diary.db`).
- Запасной ИИ-провайдер — OpenRouter (бесплатные vision-модели). Выбор провайдера — в `config.py`.
- Никаких тяжёлых зависимостей: анализы-PDF читаются нативно через Claude (без poppler).

## Конвенции

- Весь UI и тексты — по-русски, на «ты», тёплый тон, без канцелярита.
- Где источник данных не подключён — показываем **«Данных нет»**, а не прячем блок.
- Каждый новый функционал добавляем в `test_local.py` (моки для ИИ/сети, не ходить в реальные API в тестах).
- HTML экранируем (`html.escape`) везде, где выводим пользовательский текст.
- Мульти-тенант: `coach_of(bot.id)` → тренер или None (личный бот). Клиенты тренера
  привязаны через `users.coach_id` и видны в кабинете только с `consent=1`.
- Секреты только в `.env` (в git не коммитить — он в `.gitignore`).

## Как публиковать изменения («опубликуй»)

Когда владелец говорит «опубликуй» — сделай два действия:

1. **Бэкап в GitHub:** `git add -A && git commit -m "<кратко что изменил>" && git push`
2. **Выкатить на сервер** (боевой бот, Ubuntu, папка `/opt/chek`, служба `chek-bot`):
   скопировать изменённые `.py`/`.html` на сервер и перезапустить службу. НЕ трогать на
   сервере `.env` и `food_diary.db` (там боевые ключи и данные). Пример:
   `scp *.py *.html root@<SERVER_IP>:/opt/chek/ && ssh root@<SERVER_IP> "systemctl restart chek-bot"`
   (IP сервера владелец хранит у себя; спроси, если не задан.)

Перед публикацией всегда прогоняй `python test_local.py`. Правки идут в бота, которым
пользуются люди, — сначала тесты, потом публикация.

## Бэкап базы

База — главный актив («цифровой двойник» клиента), поэтому бэкап непрерывный.

- SQLite работает в режиме **WAL** (`PRAGMA journal_mode=WAL` в `db.py` → `_conn()`).
  Без WAL непрерывная репликация невозможна. Схему это не меняет.
Сейчас работают два уровня, off-site пока не в облаке:

1. **На сервере** — ночной снимок с ротацией на 14 копий: `/opt/chek/backup_db.sh`,
   запуск из `/etc/cron.d/chek-backup` в 4:00, складывает в `/opt/chek/backups/daily/`.
   Защищает от порчи и случайного удаления файла, но не от потери сервера.
2. **Off-site, на компьютер владельца** — `pull_backup.ps1` в корне проекта: просит
   сервер сделать свежий снимок, забирает его в `~/Documents/chek-backups`, держит
   30 копий. Запуск: `powershell -ExecutionPolicy Bypass -File pull_backup.ps1`.
   По расписанию — задача в «Планировщике заданий» Windows.

**litestream** (v0.3.13, `/usr/bin/litestream`, служба `litestream`) установлен, но
**не запущен**: ждёт реквизитов S3-бакета. Как появятся — кладём их в
`/etc/litestream.yml` (права 600, владелец root, в git не коммитить; шаблон без
секретов — `/etc/litestream.yml.example`), затем `systemctl enable --now litestream`.
Это заменит оба уровня выше непрерывной репликацией.

**Восстановление из ночного снимка** (пока litestream не запущен):

```
systemctl stop chek-bot
gunzip -c /opt/chek/backups/daily/food_diary_ГГГГММДД_ЧЧММСС.db.gz > /tmp/restore.db
sqlite3 /tmp/restore.db "PRAGMA integrity_check; SELECT COUNT(*) FROM users;"
cp /opt/chek/food_diary.db /opt/chek/food_diary.db.broken
cp /tmp/restore.db /opt/chek/food_diary.db
systemctl start chek-bot
```

**Восстановление через litestream** (когда он будет запущен; боевой файл сначала не трогаем):

```
systemctl stop chek-bot
litestream restore -o /tmp/restore_test.db /opt/chek/food_diary.db   # проверить копию
sqlite3 /tmp/restore_test.db "SELECT COUNT(*) FROM users;"           # убедиться, что данные на месте
cp /opt/chek/food_diary.db /opt/chek/food_diary.db.broken            # старый файл — в сторону
litestream restore -o /opt/chek/food_diary.db /opt/chek/food_diary.db
systemctl start chek-bot
```

Точка на момент времени: `litestream restore -timestamp 2026-08-27T12:00:00Z -o ...`.
Список снимков: `litestream snapshots /opt/chek/food_diary.db`.

Ручной снимок перед рискованной правкой:
`sqlite3 /opt/chek/food_diary.db ".backup '/opt/chek/backups/имя.db'"` —
именно `.backup`, а не `cp`: копия файла на живой базе может оказаться битой.

## Чек v2: разговорный ассистент

Клиентский путь — один чат, без команд и шаговых диалогов. Клиент пишет, наговаривает
или шлёт фото; `agent.handle_message` делает **один вызов Claude с tool-use** (до 5
кругов инструментов, затем финальный текст) и сам записывает, правит и отвечает фактами.

- **Персона** (`agent.PERSONA`): тёплый ассистент тренера, на «ты», коротко, в бренде
  тренера. Слово «Чек» клиенту не звучит. Никакого «неизвестный формат» и канцелярита.
- **Где что можно советовать.** В живом чате ассистент советов не даёт: отвечает
  фактами (`get_summary`), а за разбором и «что мне есть» отправляет к тренеру и зовёт
  `flag_for_trainer` → `trainer_notes`, видно в карточке клиента и в брифе. В личном
  кабинете клиент видит свои данные и **AI-разбор недели**, где мягкие практические
  замечания уместны — это письменный разбор, а не разговор. Черновиков сообщений ни в
  одном брифе нет: манера общения у тренера своя, он пишет сам. Диагнозов и назначений
  нет нигде.
- **Личный кабинет клиента** — `/me?key=<users.cabinet_token>`, страница `client.html`,
  данные из того же `client_detail`. Ключ генерится при создании пользователя, старым
  догенерён миграцией. Ссылку даёт ассистент инструментом `get_my_dashboard_link`
  URL-кнопкой. У клиента за всю жизнь три кнопки: согласие, кольцо, кабинет.
- **Инструменты** — тонкие обёртки над существующим слоем данных, схема не менялась:
  `save_meal/water/weight/wellbeing/workout`, `add_supplement`, `log_supplement_taken`,
  `remove_supplement`, `edit_last`, `delete_last`, `get_summary`, `update_profile`,
  `get_oura_link`, `flag_for_trainer`.
- **Память:** `chat_history` (последние ~15 реплик уходят в контекст, хранится больше,
  подрезается), `weight_log`, `trainer_notes`.
- **Меню Telegram** у клиента: только `/start`, `/help`, `/undo`, `/oura`. Остальные
  команды продолжают работать, но не показываются.
- **Рубильник `AGENT_MODE`** (`.env`, по умолчанию `on`). `off` — весь прежний путь
  (роутер `route_entry`, FSM-диалоги `/profile`, `/feel`, `/bad`, `/labs`) оживает как
  был. Легаси намеренно не удалён: это возможность откатиться одной строкой. Снос —
  отдельной задачей, когда v2 постоит.
- Агент требует Claude: на OpenRouter и в демо-режиме `agent.available()` = False и
  работает прежнее поведение.

## Носимые устройства

Поддерживаются два источника, оба подключаются одинаково — через OAuth по ссылке,
которую даёт ассистент в чате (`get_oura_link`, `get_whoop_link`):

- **Oura** (`oura.py`, API v2) — сон и фазы, готовность, HRV, пульс покоя, SpO2,
  активность, тренировки. Ключи: `OURA_CLIENT_ID/SECRET/REDIRECT_URI`.
- **WHOOP** (`whoop.py`, Developer API v2; v1 закрыт) — восстановление (recovery),
  HRV, пульс покоя, SpO2, температура кожи, сон с фазами и качеством, дневной strain
  и расход, тренировки. Ключи: `WHOOP_CLIENT_ID/SECRET/REDIRECT_URI`, обязателен
  scope `offline` — токен живёт около часа и обновляется по refresh.

Забор — раз в сутки после 7 утра (`_oura_daily_fetch`, `_whoop_daily_fetch`) и сразу
при подключении. Недоступный по тарифу или scope эндпоинт пропускается, весь забор
из-за него не падает. Расход тренировки берётся из совпавшей по времени записи
устройства (`kcal_source` = `oura` / `whoop`), иначе считается оценка по MET.
Если подключены оба устройства — в кабинетах показываются оба блока.

**Политика конфиденциальности** — `/privacy`, открыта без ключа (в байпасе
авторизации, как OAuth-колбэки). White-label: от лица «Health Assistant», без
упоминания платформы. Её URL указан в приложении WHOOP.

## Голосовой ввод

Клиент может наговорить вместо того, чтобы печатать: бот распознаёт речь локально
(`faster-whisper`, модель `medium`, int8, русский) и дальше ведёт текст ровно тем же
путём, что и напечатанный. Маршрутизация по состоянию FSM: шаг «описание тренировки»
и заметка самочувствия принимают транскрипт как ответ, вне диалогов — идёт в анализ еды.

- Флаг `VOICE_ENABLED` в `.env` (по умолчанию `off`). Выключено или модель не поднялась —
  бот вежливо просит написать текстом, а не падает.
- Модель качается один раз при первом голосовом и живёт в памяти процесса: первый
  голосовой после рестарта заметно медленнее, дальше быстро. Нужно ~2 ГБ RAM.
- OGG/Opus декодируется через PyAV (ставится с faster-whisper), системный ffmpeg не нужен.
- Голосовые длиннее `VOICE_MAX_SECONDS` (180 с) не берём — просим короче.

## Анонсы «что нового»

`announce.py` — разовая рассылка, запускается **руками** после выката:

```
cd /opt/chek && ./.venv/bin/python announce.py --dry-run "текст"   # посчитать получателей
cd /opt/chek && ./.venv/bin/python announce.py "текст"             # разослать
```

Бот про этот модуль не знает — сам на рестарте ничего не разошлёт. Каждому пишет тот
бот, в котором он зарегистрирован; клиентам тренера — только с `consent=1` и нейтральным
тоном, без упоминания «Чека»: для клиента это ассистент его тренера. Заблокировавшие бота
пропускаются, лимиты Telegram обрабатываются (пауза + повтор).

## Напоминания

Клиент задаёт их словами: «напоминай пить воду каждые 2 часа», «напомни про магний
в 22:00», «про воду больше не напоминай». Агент разбирает фразу инструментами
`set_reminder` / `list_reminders` / `update_reminder` / `delete_reminder`, запись
ложится в таблицу `reminders` (время `time` **или** интервал `every_min` с окном
`win_from`/`win_to`, плюс `dow_mask` по дням недели).

Шлёт `reminder_loop` в `bot.py`: раз в ~20 секунд смотрит `db.due_reminders`,
дедуп через `_fire_once`. Формулировки варьируются (`REMINDER_PHRASES`), текст
уходит и в `chat_history` — чтобы ответ «выпил» агент понял в контексте.
Умные пропуски (`reminder_skip`): вода — если дневная норма уже выполнена; БАД —
если отмечен сегодня; тренировка — если уже записана. Тихие часы 23:00–08:00
действуют **только на интервальные**: попросил «в 23:30» — пришлём в 23:30.

Старые захардкоженные напоминания (вода, план тренировок, вечерняя сводка)
заводятся один раз в `seed_reminders` как обычные записи — дальше клиент
управляет ими словами, и выключенное не возвращается. Вечерняя сводка живёт под
`kind='evening'` и по-прежнему шлёт разбор дня, а не короткую фразу.

**Часовой пояс: пока всё по времени сервера (МСК).** Поле `users.tz` в схеме
есть, но логика на него не опирается — клиенту в другом поясе напомнит по
московскому времени. Чинить, когда появятся клиенты вне МСК.

## Журнал решений (кратко)

- Имя **«Чек»**: Пол Чек + чек-проверка + метафора «check engine» (индикаторы здоровья).
- Основной покупатель — тренер, не конечный пользователь. White-label обязателен.
- Сервер — российский хостер с **зарубежной локацией** (иначе Claude API недоступен из РФ).
- Анализы — вход простой PDF/фото любой лаборатории; парсит Claude.
- БАДы — простой список + ИИ-проверка совместимости (не назначение).
- **Разделение ролей: бот собирает, тренер интерпретирует.** Клиент-facing бот (бот
  тренера) собирает и подтверждает данные, но не даёт клиенту советов, оценок и разборов:
  ни рекомендаций по еде, ни трактовки анализов, ни советов по БАДам. Вся интерпретация
  идёт тренеру — в недельный AI-бриф и кабинет, там ИИ советует в полную силу. Причина:
  ядро ценности продукта — личность тренера; бот, который советует сам, обесценивает его
  и лезет в медицинскую зону. Числа и факты (КБЖУ, балл Чека, суммы за день, что вне
  нормы) — это данные, их клиенту показываем. В личном боте владельца ограничение не
  действует: там пользователь сам себе тренер. Исключение включается тренером:
  `coaches.ai_tips` (команда `/aitips on` в боте тренера) возвращает боту полный
  режим — разборы, советы и бриф недели по `/today`. По умолчанию флаг выключен.
